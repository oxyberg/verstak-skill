# Верстак

Воспроизводить интерфейс из Figma в коде с визуальным соответствием 1:1. Считать макет, его компоненты, переменные, стили, ассеты, Auto Layout и constraints источником истины. Делать допущения только для адаптивности под размер окна, динамического контента и состояний, которых нет в макете.

## Обязательный процесс

### 1. Проверить Figma MCP

Перед анализом макета прочитать [references/figma-mcp.md](references/figma-mcp.md).

1. Найти доступные Figma MCP-инструменты и определить провайдер: официальный/базовый Figma MCP либо `@gethopp/figma-mcp-bridge`.
2. Выполнить безопасный read-only вызов, подтверждающий доступ к нужному файлу или выбранному узлу. Не считать одно лишь наличие конфигурации подтверждением работоспособности.
3. Для bridge проверить, что Figma-плагин открыт в нужном файле и файл виден через `list_files` либо эквивалентный вызов.
4. При отсутствии или ошибке подключения остановить работу с макетом, назвать конкретную неисправность и помочь настроить один из поддерживаемых вариантов. Не подменять недоступный Figma-контекст догадками или ручным разбором превью.

### 2. Изучить проект и источник дизайна

1. Найти точный Figma-фрейм, компонент или вариант, который нужно реализовать. Если ссылка ведёт на слишком крупный узел, сначала получить карту структуры, затем запросить только нужные дочерние узлы.
2. Получить одновременно структурированный design context и эталонный screenshot. Для bridge использовать ближайшие эквиваленты `get_design_context`/`get_node` и `get_screenshot`.
3. Исследовать репозиторий: определить стек, существующие компоненты, стили, токены, шрифты, ассеты, layout-примитивы и правила проекта. Соблюдать уже принятые архитектуру и соглашения.
4. Зафиксировать размеры эталонных фреймов и viewport до начала реализации.

### 3. Найти дизайн-систему

1. Самостоятельно искать дизайн-систему в коде и Figma: библиотеки, переменные, локальные стили, component sets, variants, Code Connect и уже реализованные компоненты.
2. Если найдено несколько систем, доступ к библиотеке закрыт или связь неоднозначна, задать пользователю один конкретный вопрос. Не спрашивать то, что можно достоверно установить через код или MCP.
3. При наличии дизайн-системы переиспользовать её компоненты и токены. При необходимости выгрузить недостающие разрешённые стили и ассеты из Figma.
4. Если дизайн-системы нет, не придумывать токены, названия токенов, иконки, цвета, типографику, радиусы, тени или интервалы. Использовать точные значения из Figma и экспортировать исходные SVG/растровые ассеты. Не подключать библиотеку иконок ради замены доступных Figma-ассетов.

### 4. Понять структуру и декомпозировать

1. Прочитать иерархию слоёв, Auto Layout, constraints, grids, clipping, absolute positioning, component instances, variants и вложенные контейнеры.
2. Для экрана выделить модули, затем разложить каждый модуль на молекулы и атомы.
3. Для отдельного компонента выделить составные атомы, slots, варианты, состояния и публичный API.
4. Переиспользовать повторяющиеся сущности, но не создавать абстракцию из одноразового элемента только ради формальной атомарности.
5. Сохранять семантику и границы контейнеров из Figma. Не «расплющивать» вложенность, если она управляет размерами, выравниванием, обрезкой или адаптивностью.

### 5. Реализовать точную геометрию и визуал

1. Перенести 1:1 размеры, spacing, padding, alignment, цвета, границы, радиусы, тени, blur, opacity, типографику, line height, letter spacing, иконки и изображения.
2. Сохранять intrinsic aspect ratio и режимы `fill`, `fit`, `crop` согласно Figma.
3. Предпочитать layout-модель, соответствующую Auto Layout и constraints, вместо хрупкого набора абсолютных координат. Использовать absolute positioning только там, где он есть в структуре макета или необходим для перекрытий.
4. Не воспроизводить системную обвязку из демонстрационного макета: рамку браузера, адресную строку, системный status bar, home indicator, клавиатуру и другие элементы, которые предоставляет платформа. Реализовывать их только при явном указании, что они являются частью продукта.
5. Не заменять точные ассеты похожими символами, emoji, CSS-фигурами или иконками из стороннего пакета.

### 6. Реализовать состояния и анимацию

1. Найти component variants, prototype interactions, hover/pressed/focus/disabled/loading/error states и motion styles. Проверить не только выбранный узел, но и связанный component set.
2. Реализовать найденные состояния и переходы с указанными easing, duration, delay и изменяемыми свойствами.
3. Если состояния не заданы, самостоятельно добавить необходимые hover, focus-visible, pressed и disabled состояния, не меняя визуальный язык макета. Добавить короткую уместную анимацию и отметить эти решения как выведенные, а не извлечённые из Figma.
4. Учитывать клавиатуру, reduced motion и доступность. Не делать анимацию препятствием для взаимодействия.

### 7. Реализовать адаптивность

1. Найти alternate frames, breakpoints, Auto Layout resizing, min/max sizes, wrapping, constraints и поведение контейнеров.
2. Реализовать явно заданные изменения на контрольных размерах.
3. Если ресайзы не заданы, вывести поведение из контейнеров и содержания: сохранить иерархию, приоритеты, читаемость, touch targets и отсутствие непреднамеренного overflow. Считать такие правила допущениями.
4. Проверить как минимум эталонный viewport, соседний меньший и соседний больший размер, если платформа допускает изменение окна.

### 8. Сверить pixel perfect

1. Запустить проект и снять screenshot реализации в точном размере эталонного Figma-фрейма.
2. Сравнить изображения визуально и, когда возможно, через overlay или pixel diff. Проверить геометрию, baseline текста, clipping, цвета, тени, радиусы и ассеты.
3. Исправлять расхождения итеративно. Не объявлять работу завершённой после одного прохода и не оценивать соответствие только по коду.
4. Отдельно проверить интерактивные состояния, анимацию, адаптивные размеры и динамический контент.
5. Запустить релевантные тесты, lint и typecheck проекта.

## Критерии завершения

Завершать работу только когда:

- MCP реально прочитал нужный Figma-файл или узел;
- структура компонентов соответствует смысловым контейнерам макета;
- переиспользована доступная дизайн-система, а отсутствующие токены и ассеты не выдуманы;
- эталонный размер совпадает с макетом 1:1, кроме явно перечисленных технических ограничений;
- состояния, motion и адаптивность реализованы и проверены;
- системная обвязка платформы не продублирована;
- итоговый ответ перечисляет реализованное, проверки, допущения и оставшиеся отклонения.
